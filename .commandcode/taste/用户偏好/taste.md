# 用户偏好
- 用中文交流，回复也使用中文。Confidence: 0.8
- 发版出包走 CI：重打 git tag 并把 tag push 到 origin 触发 GitHub Actions（release.yml）自动打各平台安装包并发布 Release，而不是在本地打包。Confidence: 0.6
- 允许重打/移动已有的发布 tag（例如把 v1.0.0-rc.1 重新指向 main HEAD），不介意同一 tag 的指向发生变更。Confidence: 0.65
- 要求把 rc / 预发布版本在 GitHub 上标记为 prerelease（`gh release edit <tag> --prerelease`），让 `/releases/latest` 继续指向稳定版而不是 RC。Confidence: 0.5
- 期望分发包与界面都自洽、不出现预期外的多余包裹项：插件/包要含真实实现代码（而非仅元数据/声明），且应同时包含 desktop 实现与 mobile 实现两部分（如「包里应该包含 2 部分实现：desktop 实现、mobile 实现」）；同一岗位包内嵌或由运行时合成的派生条目应并回该插件，不得在设置页「已装」列表里单独列为第二个包（用户会明确给出这类归属规则，并直接给出期望的包数量，如「只要 3 个插件包」）；发现不符会当作 bug 追问根因。Confidence: 0.7
- 坚持「岗位/领域特有的内容归岗位包所有」：宿主与基础包不得硬编码某个岗位的角色、能力或文案（如 codeAgent 属于 software-engineering），没装对应岗位包时这类内容不应出现在界面（角色映射等）里；范围不止声明与文案，也包括实现代码本身——只有某岗位（如 software-engineering 的 repo：克隆/索引/符号扫描/工具循环）才用得到的宿主实现，也应放进该岗位包，基础包只留与岗位无关的基础设施。Confidence: 0.7
- 架构重构类的改动要求功能等价（parity）：装上某个包（如 software-engineering）后的能力、页面、题型必须与重构前一致，不接受能力缩水。Confidence: 0.5
- 要求把「合成/中间产物」性质的概念从代码里彻底清除，而不是保留兼容层：一旦某个 id / 类型 / 名册只是运行期拼出来的、不真实存在，就应连同合成器、退役名册、保留名、归一化函数一起删干净，不给它留「历史说明」式残骸。Confidence: 0.6
- rc / 预发布阶段接受破坏性变更：不要求为已落库的历史数据做回填或读时兼容，宁可让旧数据失效（重选一次即恢复），也不要为兼容长期背一层代码。Confidence: 0.55
- 当文档与既定设计决定不一致时，先修文档再改代码：明确要求「先把文档里不对的地方改对了，再改代码」——文档是设计与验收的依据，错误表述（如「只能声明宿主已实现的东西」）必须先改对，代码迁移随后。Confidence: 0.7
- 中文文档里引号统一用「」，不用 ASCII 双引号包裹词句（改文档时会把 `"..."` 逐个换成 `「...」`）。Confidence: 0.5
- 以「文档即目标规格」推进改动：评审后先把文档改成目标形态，再让代码按文档补齐；用户会用一句状态差点明这种落差（如「之前 review 完，文档更新了，代码还没实现」）就直接要 agent 落地实现，不再复述需求。Confidence: 0.55
- 指令写得极简短（如"处理"、"重打 v1.0.0-rc.1，并先删掉 release"、"现在开始修改"，甚至只回一个"弄"表示同意照做），报问题也只丢一句症状（如"打出的插件还是 json,"），指望 agent 自己从前文补全上下文、定位根因并直接动手，不需要冗长确认。Confidence: 0.6
- 插件分发包要用项目自定义的压缩包格式（扩展名 .ojb），而不是裸 JSON 或未打包的目录：打包/分发环节应产出该压缩格式的包。Confidence: 0.5
